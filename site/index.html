PROOF OF SLEEP

Humans sleep.
Machines don't.

748,667 NEAR accounts were active in the first two weeks of October 2026. Only 61,957 were active on at least 5 of those days. 5,771 of them keep a sleep-sized quiet stretch the way a person does.

Try:

Three real accounts from NEAR, names removed. Each row is one day; each mark is an hour with at least one transaction, in UTC.

What the test found

We took the first two weeks of every month since January 2021 and looked at when each account signs transactions. Over two weeks, an account passes if it uses at least 6 different hours of the clock, never touches a stretch of 5 to 14 hours in a row, and that stretch is longer than chance would produce.

Active accounts or actual people?

In the latest window 748,667 accounts were active, but 668,994 of them showed up on only one or two days, up from 60,870 the month before. The count of active accounts swings on bursts like that. The accounts that pass the test barely move with it: monthly changes correlate at 0.19.

sql/00_account_windows.sql

-- Step 0. One row per account per 14-day window, with its daily rhythm features.
-- Everything else reads this table, so the expensive scan of `transactions` happens once.
-- The filter on block_date is literal: only the sampled days are read and billed.
-- Not partitioned by date on purpose: BigQuery's free tier deletes date partitions older than 60 days.
CREATE OR REPLACE TABLE `your-project.proof_of_sleep.account_windows`
CLUSTER BY window_start, class AS
WITH slots AS (                             -- one row per account, day and hour with activity
  SELECT
    signer_account_id AS account,
    DATE_TRUNC(block_date, MONTH) AS window_start,
    block_date,
    EXTRACT(HOUR FROM block_timestamp_utc) AS hour,
    COUNT(*) AS n_tx
  FROM `bigquery-public-data.crypto_near_mainnet_us.transactions`
  WHERE block_date BETWEEN ... -- 70 two-week windows, listed in pipeline/config.py
  GROUP BY 1, 2, 3, 4
),
days AS (                                   -- which hours each active day used
  SELECT
    account, window_start, block_date,
    SUM(n_tx) AS n_tx,
    COUNT(*) AS n_slots,
    BIT_OR(1 << hour) AS day_mask
  FROM slots
  GROUP BY 1, 2, 3
),
accounts AS (                               -- all the hours of the clock the account ever used
  SELECT
    account, window_start,
    SUM(n_tx) AS n_tx,
    COUNT(*) AS n_days,
    SUM(n_slots) AS n_slots,
    BIT_OR(day_mask) AS hour_mask
  FROM days
  GROUP BY 1, 2
),
hours AS (
  SELECT *, ARRAY(SELECT h FROM UNNEST(GENERATE_ARRAY(0, 23)) AS h WHERE (hour_mask >> h) & 1 = 1) AS hs
  FROM accounts
),
gaps AS (                                   -- the longest stretch of hours never used, wrapping past midnight
  SELECT *,
    (SELECT AS STRUCT gap, start_h
     FROM (
       SELECT h AS start_h,
              COALESCE((SELECT MIN(h2) FROM UNNEST(hs) AS h2 WHERE h2 > h), hs[OFFSET(0)] + 24) - h - 1 AS gap
       FROM UNNEST(hs) AS h
     )
     ORDER BY gap DESC, start_h
     LIMIT 1) AS g
  FROM hours
),
classified AS (
  SELECT
    account, window_start, n_tx, n_days, n_slots, hour_mask,
    ARRAY_LENGTH(hs) AS n_hours,
    g.gap AS gap,
    -- middle of the quiet stretch, as a clock hour (UTC)
    (g.start_h + 1 + g.gap / 2) - 24 * FLOOR((g.start_h + 1 + g.gap / 2) / 24) AS mid,
    CASE
      WHEN n_days < 5 THEN 'too_few'
      WHEN g.gap <= 2 AND n_slots / n_days >= 8 THEN 'machine'
      WHEN ARRAY_LENGTH(hs) <= 3 THEN 'timer'
      WHEN g.gap >= 5 AND g.gap >= [99,99,99,20,17,15,13,12,11,10,9,8,7,7,6,6,5,5,4,4,3,3,99,99,99][OFFSET(ARRAY_LENGTH(hs))] AND g.gap <= 14 AND ARRAY_LENGTH(hs) >= 6 THEN 'sleeper'
      WHEN g.gap >= 5 AND g.gap >= [99,99,99,20,17,15,13,12,11,10,9,8,7,7,6,6,5,5,4,4,3,3,99,99,99][OFFSET(ARRAY_LENGTH(hs))] THEN 'routine'
      ELSE 'unclear'
    END AS class
  FROM gaps
)
SELECT                                      -- accounts seen on 1-2 days are kept only as counts
  IF(n_days >= 3, account, '_light_') AS account,
  window_start,
  COUNT(*) AS accounts,
  SUM(n_tx) AS n_tx,
  n_days,
  SUM(n_slots) AS n_slots,
  IF(n_days >= 3, ANY_VALUE(hour_mask), NULL) AS hour_mask,
  IF(n_days >= 3, ANY_VALUE(n_hours), NULL) AS n_hours,
  IF(n_days >= 3, ANY_VALUE(gap), NULL) AS gap,
  IF(n_days >= 3, ANY_VALUE(mid), NULL) AS mid,
  IF(n_days >= 3, ANY_VALUE(class), 'light') AS class
FROM classified
GROUP BY 1, 2, n_days

Who actually sends the transactions?

Accounts that never sleep sent 74% of all transactions in the latest window. Of the 100 busiest accounts, 99 are machines and 0 sleep, and those 100 sent 72% of everything. Some of this traffic is relayers acting for other accounts: such delegated actions from accounts that do not themselves look like machines were 13% of all transactions.

sql/07_concentration.sql

-- How concentrated are transactions? Share of each window's transactions sent by the
-- busiest accounts. Aggregate counts only.
WITH ranked AS (
  SELECT
    window_start,
    n_tx,
    class,
    ROW_NUMBER() OVER (PARTITION BY window_start ORDER BY n_tx DESC, account) AS rnk
  FROM `your-project.proof_of_sleep.account_windows`
  WHERE account != '_light_'
)
SELECT
  window_start,
  SUM(n_tx) AS txs_in_table,
  SUM(IF(rnk <= 10, n_tx, 0)) AS top_10,
  SUM(IF(rnk <= 100, n_tx, 0)) AS top_100,
  SUM(IF(rnk <= 1000, n_tx, 0)) AS top_1000,
  COUNTIF(rnk <= 100 AND class = 'machine') AS top100_machines,
  COUNTIF(rnk <= 100 AND class = 'sleeper') AS top100_sleepers
FROM ranked
GROUP BY 1
ORDER BY 1

Does the test work?

These are checks on our own method, including the one that went against it.

Does the test find real people?

NEAR's I-Am-Human registry holds 5,014 accounts verified as unique humans by a face scan. Of the windows where they were regularly active, 25% pass, against 1.9% of accounts with their days shuffled. So the test does find people, but it misses most of them, and it misses more over time: 33% of verified windows passed in 2023 and 15% in 2026.

Did they follow their clocks?

When clocks change, people who observe daylight saving should move by an hour. Across 4 clock changes the average move was -0.05 hours in the expected direction (95% interval -0.26 to +0.16). A full one-hour move is ruled out. Either few of these accounts live where clocks change, or they do not follow local time. This data cannot say which.

  • How far ordinary weeks drift on their own
  • Each clock change: how far sleepers moved, compared with an Asian control group

sql/08_dst.sql

-- Natural experiment: when clocks change, do accounts move with them?
-- 1. Take accounts that pass the sleep test in the 14 days before a clock change.
-- 2. Sort them into regions using only where their quiet stretch sat BEFORE the change.
-- 3. Count when those same accounts were active before and after the change.
-- Placebo events use ordinary dates with no clock change anywhere.
-- Output is counts per event, group, period and hour: never individual accounts.
WITH slots AS (
  SELECT signer_account_id AS account, block_date, EXTRACT(HOUR FROM block_timestamp_utc) AS hour
  FROM `bigquery-public-data.crypto_near_mainnet_us.transactions`
  WHERE block_date BETWEEN ... -- days around each clock change, see pipeline/dst_events.py
  GROUP BY 1, 2, 3
),
tagged AS (
  SELECT e.event, IF(s.block_date <= e.pre_end, 'pre', 'post') AS period, s.account, s.block_date, s.hour
  FROM slots AS s
  JOIN UNNEST([ ... the clock-change dates, see pipeline/dst_events.py ... ]) AS e
    ON s.block_date BETWEEN e.pre_start AND e.pre_end
    OR s.block_date BETWEEN e.post_start AND e.post_end
),
days AS (
  SELECT event, period, account, block_date,
         COUNT(*) AS n_slots,
         BIT_OR(1 << hour) AS day_mask,
         ARRAY_AGG(hour) AS hours
  FROM tagged
  GROUP BY 1, 2, 3, 4
),
periods AS (
  SELECT event, period, account,
         COUNT(*) AS n_days,
         SUM(n_slots) AS n_slots,
         BIT_OR(day_mask) AS hour_mask,
         ARRAY_CONCAT_AGG(hours) AS hours
  FROM days
  GROUP BY 1, 2, 3
),
with_hours AS (
  SELECT *, ARRAY(SELECT h FROM UNNEST(GENERATE_ARRAY(0, 23)) AS h WHERE (hour_mask >> h) & 1 = 1) AS hs
  FROM periods
),
features AS (
  SELECT event, period, account, n_days, n_slots, hours, ARRAY_LENGTH(hs) AS n_hours,
    (SELECT AS STRUCT gap, start_h
     FROM (
       SELECT h AS start_h,
              COALESCE((SELECT MIN(h2) FROM UNNEST(hs) AS h2 WHERE h2 > h), hs[OFFSET(0)] + 24) - h - 1 AS gap
       FROM UNNEST(hs) AS h
     )
     ORDER BY gap DESC, start_h
     LIMIT 1) AS g
  FROM with_hours
),
pivoted AS (                                  -- both periods side by side for each account
  SELECT event, account,
    MAX(IF(period = 'pre', n_days, NULL)) AS n_days,
    MAX(IF(period = 'post', n_days, NULL)) AS post_days,
    MAX(IF(period = 'pre', n_slots, NULL)) AS n_slots,
    MAX(IF(period = 'pre', n_hours, NULL)) AS n_hours,

-- How much does the count depend on the thresholds? Recounts sleepers under other choices,

  FROM `your-project.proof_of_sleep.account_windows`
  WHERE account != '_light_'

  window_start,

-- Do accounts come back? For every window and class: of the accounts in that class,

sql/12_relayed.sql

-- Humans who never sign. When a relayer pays gas for someone, the relayer signs the transaction
-- and the person only appears as the receiver of a DELEGATE_ACTION. This runs the same sleep test
-- on those people, for the windows in 2026-04-01, 2026-10-01.
WITH acted AS (
  SELECT
    DATE_TRUNC(block_date, MONTH) AS window_start,
    receipt_receiver_account_id AS account,
    block_date,
    EXTRACT(HOUR FROM block_timestamp_utc) AS hour,
    COUNT(*) AS n
  FROM `bigquery-public-data.crypto_near_mainnet_us.receipt_actions`
  WHERE (block_date BETWEEN ... -- see pipeline/config.py) AND action_kind = 'DELEGATE_ACTION'
  GROUP BY 1, 2, 3, 4
),
days AS (
  SELECT window_start, account, block_date, SUM(n) AS n, COUNT(*) AS n_slots, BIT_OR(1 << hour) AS day_mask
  FROM acted
  GROUP BY 1, 2, 3
),
accounts AS (
  SELECT window_start, account, SUM(n) AS n, COUNT(*) AS n_days, SUM(n_slots) AS n_slots, BIT_OR(day_mask) AS hour_mask
  FROM days
  GROUP BY 1, 2
),
hours AS (
  SELECT *, ARRAY(SELECT h FROM UNNEST(GENERATE_ARRAY(0, 23)) AS h WHERE (hour_mask >> h) & 1 = 1) AS hs
  FROM accounts
),
gaps AS (
  SELECT *,
    (SELECT AS STRUCT gap, start_h FROM (
       SELECT h AS start_h,
              COALESCE((SELECT MIN(h2) FROM UNNEST(hs) AS h2 WHERE h2 > h), hs[OFFSET(0)] + 24) - h - 1 AS gap
       FROM UNNEST(hs) AS h) ORDER BY gap DESC, start_h LIMIT 1) AS g
  FROM hours
),
classified AS (
  SELECT window_start, account, n, CASE
      WHEN n_days < 5 THEN 'too_few'
      WHEN g.gap <= 2 AND n_slots / n_days >= 8 THEN 'machine'
      WHEN ARRAY_LENGTH(hs) <= 3 THEN 'timer'
      WHEN g.gap >= 5 AND g.gap >= [99,99,99,20,17,15,13,12,11,10,9,8,7,7,6,6,5,5,4,4,3,3,99,99,99][OFFSET(ARRAY_LENGTH(hs))] AND g.gap <= 14 AND ARRAY_LENGTH(hs) >= 6 THEN 'sleeper'
      WHEN g.gap >= 5 AND g.gap >= [99,99,99,20,17,15,13,12,11,10,9,8,7,7,6,6,5,5,4,4,3,3,99,99,99][OFFSET(ARRAY_LENGTH(hs))] THEN 'routine'
      ELSE 'unclear'
    END AS relayed_class
  FROM gaps
)

Did value follow the people?

Since January 2025 the number of accounts passing the test fell 93%. Over the same stretch two-week swap volume through NEAR Intents grew from $1.1M to $2B, and the price went from $5.32 to $5.07 after a low of $1.08. More money flows through NEAR while fewer accounts that look like people use it.

Does anything lead the price?

Monthly changes in the number of accounts passing the test do not lead the price by 1, 2 or 3 months (best correlation +0.14, p = 0.31). 4 of the 28 tests in this table cross p < 0.05 where about 1.4 are expected by chance, a borderline excess. The strongest result runs the other way: price moves first and active accounts follow one month later.
