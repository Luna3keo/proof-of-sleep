# Method

Every number in this file is generated by `python rebuild.py`.

## Data

| Source | Used for | Access |
| --- | --- | --- |
| `bigquery-public-data.crypto_near_mainnet_us` | who signed what, and when | free tier, needs a Google account |
| NEAR I-Am-Human registry (`registry.i-am-human.near`) | accounts verified as human | public RPC, no key |
| NearBlocks `/v1/charts` | price, market cap, cross-check of counts | no key |
| DefiLlama `summary/*/near-intents`, `summary/fees/near` | NEAR Intents volume, chain fees | no key |
| FastNEAR `tx.main.fastnear.com` | the live check on the dashboard | no key, from the browser |

The NEAR dataset is stored in BigQuery's `us-east1` region. Jobs and the helper table must run there, or BigQuery reports a misleading access error.

## Sampling

The first 14 days of every month from January 2021 to October 2026: 70 windows. Fourteen days is exactly two full weeks, so every weekday appears twice. All windows are read with literal `block_date` ranges, so BigQuery prunes partitions and bills only these days. The main scan reads two columns from `transactions` and costs 91 GB. The full pipeline reads about 132 GB, well inside BigQuery's free 1 TiB a month.

## The sleep test

Inputs for each account and window, from `signer_account_id` and `block_timestamp_utc`:

- `n_days`: days with at least one signed transaction.
- `n_hours`: how many of the 24 UTC hours were ever used.
- `gap`: the longest run of never-used hours, wrapping past midnight. It is the time of day when the account was quiet on *every* day.
- `n_slots`: the number of (day, hour) pairs with activity, so `n_slots / n_days` is active hours on a typical active day.

The rules, applied in order:

| Class | Rule | Meaning |
| --- | --- | --- |
| `too_few` | fewer than 5 active days | not enough to judge |
| `machine` | `gap` of 2 hours or less, and 8+ active hours on a typical day | active around the clock |
| `timer` | 3 or fewer different hours used | fires in the same hour or two every day |
| `sleeper` | a quiet stretch longer than chance, of 5 to 14 hours, using 6+ different hours | a day and a night |
| `routine` | a quiet stretch longer than chance, but narrower activity | a person's habit or a scheduled job; timing cannot tell which |
| `unclear` | anything else | active, with no clear pattern |

Accounts active on only 1 or 2 days are stored as counts in `light` rows. No per-account row for them leaves BigQuery.

**"Longer than chance."** Given how many different hours an account used, [`pipeline/contiguity.py`](pipeline/contiguity.py) computes exactly how likely a quiet stretch at least this long would be if the used hours were random. The stretch must be unlikely at the 0.05 level.

The SQL in [`sql/00_account_windows.sql`](sql/00_account_windows.sql) and the Python in [`pipeline/sleep.py`](pipeline/sleep.py) implement the same rules. [`tests/test_sleep.py`](tests/test_sleep.py) proves they agree on 900 real accounts (names removed). [`site/test.html`](site/test.html) proves the browser version agrees too.

## Validation

**Against verified humans.** The I-Am-Human registry lists 5,014 accounts verified as unique humans by a face scan. In the 18,442 account-windows where they were active on at least 5 days, 25% pass the test, 5% show a narrow routine, 1% look like machines. In the same windows 13% of all regular accounts pass. The thresholds were chosen with this group in view, so its pass rate is somewhat flattering; the table of variations on the dashboard shows how much it moves. These are shares of account-windows, not of accounts. The pass rate has fallen over time: 33% in 2023, 22% in 2024, 15% in 2026 (last 12 windows: 15%).

**Against chance.** 8,745 randomly chosen accounts from 1-14 October 2026, with each day's activity rotated around the clock by a random amount. 1.9% pass, against 9% for the real accounts, so about 21% of accounts that pass could be chance. Quiet stretches peak at 7 hours for verified humans, 8 for accounts in general and 4 when shuffled.

**Independent counts.** Window-level transaction totals match NearBlocks within 1% in 70 of 70 windows, worst ratio 1.0031 (Dec 2024). Daily transaction counts over the last 69 days match within 1% on 69 of 69 days, and active accounts on 69 of 69 days.

**Clock changes.** Accounts are grouped by where their quiet stretch sits before a daylight-saving change, then the same accounts are compared in the 14 days before and after. Groups in Europe and the Americas should move by an hour, an Asian control group should not, and placebo dates with no clock change measure ordinary drift. Across 4 clock changes the average move in the expected direction was -0.05 hours (95% interval -0.26 to +0.16). A full one-hour move is ruled out. I did not find the shift, and I do not know whether that is because few of these accounts live where clocks change or because they do not follow local time. Only the 2026 clock changes are included, to stay within the shared free quota.

**Sensitivity.** Each rule changed one at a time moves the latest count by -65% to +30%. Dropping the chance test multiplies it by 5.3.

**Weekends.** An earlier version compared weekday and weekend activity. Sleepers and machines looked almost the same, so the check said nothing either way and was dropped.

## How many regular people could there be?

If real people pass at rate *s* and everything else at rate *f*, then the share of regular accounts that are people is (*p* − *f*) / (*s* − *f*), where *p* is the observed pass rate (9.3% here). Neither rate is known well. *s* is 25% over all years and 15% in the last 12 windows. *f* is 1.9% for shuffled accounts, but real bots may pass more often, and no labelled set of them exists. Across those values the answer runs from about 1,200 to about 34,400, so this project does not publish a single figure.

## Single-program clusters

A real population of people spreads across time zones. Some windows contained large groups of accounts sleeping in the same few hours, which looks like one program or one place. Rule: a family of accounts (`.tg`, `.kaiching`, implicit, and so on) with at least 1,000 sleepers and more than 50% of them in three neighbouring clock hours is excluded from the count for that window. It flags 4 family-windows: `kaiching` (Sep 2023, Oct 2023, Nov 2023); `implicit` (Oct 2024). The latest window is not affected.

## People behind relayers

A relayer signs for someone who only appears as the receiver of a `DELEGATE_ACTION` (NEP-366 requires the transaction receiver to be the delegating account). Running the same test on those receivers ([`sql/12_relayed.sql`](sql/12_relayed.sql)) adds 4,203 accounts in the latest window, of which 4,119 have no signing record on 3 or more days. This is measured for two windows only, because reading `receipt_actions` costs far more than `transactions`.

## Limits

- The test measures rhythm. It cannot prove any account is a person, and it cannot tell one person from many accounts.
- It misses three out of four verified humans.
- No labelled set of scheduled bots exists, so the false-pass rate on them is unknown.
- Hour resolution only.
- It cannot see people who sign off-chain, including most NEAR Intents users.
- Windows are 14 days from the start of each month, so spikes between windows are missed.
- The single-program exclusion is a judgement encoded as a rule. It is in `pipeline/analyze.py` and easy to change.

## Corrections made after an independent review

An earlier version of this analysis was audited by a separate reviewer, who found real errors. What changed: (1) the original rule was replaced by the rule above, which requires a sleep-sized quiet stretch that is longer than chance. Accounts that pass are still typically active in only one or two hours of a given day; the rule is about which hours are never used across two weeks; (2) the "machine" label required only activity across the whole window, and now requires many active hours on a typical day; (3) a chart claimed to validate the method but was produced by the rule itself and was removed; (4) the outside check on verified humans was added; (5) the headline ratio was affected by a one-week burst of accounts, which is now disclosed; (6) the share of transactions from the top 100 accounts used the wrong total and was corrected; (7) the retention comparison was redone with the new classes and now excludes single-program windows; (8) a single "estimated people" figure was withdrawn, because it hid how much it depended on two unknown rates; the count was also wrongly called a floor.

## Privacy

The repository publishes aggregates only. No account name appears in `data/raw/` except contracts in `apps.csv`, and bare `.tg` names are removed from that file because they are personal accounts. The list of verified accounts is read from the public chain and kept out of the repository. The live check runs in the visitor's browser against public data and stores nothing.

## Rebuilding

```bash
python rebuild.py                 # from data/raw: seconds, no network, no keys
python rebuild.py --check         # same, and verifies the published hash
python rebuild.py --from-bigquery # re-pulls data/raw first
```

For `--from-bigquery`, set `BQ_PROJECT` in `.env` (any Google Cloud project, the free BigQuery sandbox works), run `gcloud auth login`, and allow a few minutes. Every statement has a byte cap, and it refuses to run if the estimate is over it. `python -m pipeline.pull_bigquery --plan` prints the planned bytes; steps after step 00 can only be planned once step 00 has built its table.

**How the committed data was made.** The features in step 00 were computed once from the raw table. When the rules changed, the final classification was applied to those stored features instead of repeating a 91 GB scan, using the same `CASE` expression that is in `sql/00_account_windows.sql`. The final SQL was then run from scratch on one 14-day window, and it matched the Python on all 75,090 accounts in that window. A complete re-run of step 00 with the final SQL has not been done. Queries for the clock-change, relayed and contract steps were re-run with the final rules.
